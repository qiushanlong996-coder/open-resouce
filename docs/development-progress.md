## 环境与人工安装事项

- 自动安装或自动配置环境失败时，必须立即在本节记录，并通知项目负责人手动处理。
- 记录内容必须包含：目标机器、软件名称、准确版本、用途、安装或验证命令、是否阻塞当前功能。
- 当前本机没有系统级 Go。开发流程临时使用工作区内 Go 1.24.6，不阻塞当前开发。
- 当前服务器没有安装 Go。Gateway 使用本地交叉编译的静态二进制部署，不阻塞当前开发。
- 服务器 Docker 镜像源连接不稳定。进入数据库与中间件 Compose 部署前需要再次验证；若仍失败，需要项目负责人协助手动配置稳定镜像源。
- 已解决：HTTPS 连接 GitHub 443 连续超时。2026-07-26 已生成并添加专用 ed25519 密钥，GitHub SSH 认证成功，仓库远程地址已切换为 SSH。
- 2026-07-31：新 macOS 开发机初始无 Go。brew 从 ghcr.io 下载极慢不可用；已由项目负责人通过阿里云镜像安装官方 Go 1.24.6 pkg（/usr/local/go），并将 GOPROXY 设为 goproxy.cn，不阻塞开发。
- 2026-07-31：本机无 pnpm，且 apps/web 的 package-lock.json 已过期；前端依赖统一使用 `npx pnpm@10 install --frozen-lockfile` 安装（与 pnpm-lock.yaml 一致），不阻塞开发。
- 2026-08-05：新增第三台机器「分析服务器」（Ubuntu 22.04，8 核 8G），专跑用户上传代码包的分析作业。
  **该机器 npm 官方源不可达**：`registry.npmjs.org` 与 `nodejs.org` curl 均返回 000（超时），
  必须改用 `registry.npmmirror.com` 与 `mirrors.aliyun.com`，否则装依赖会长时间无响应且不报错。
  **apt 默认源同样不可达**（archive.ubuntu.com 超时）。坑点：`apt-get update -qq` 会返回 rc=0，
  因为索引下载失败只是 warning、会退回旧缓存——判断可用性要看有没有 `Failed to fetch`，别只看退出码。
  已换成 `mirrors.aliyun.com`。出厂无 swap，已加 4GB swapfile。
  SSH 为**非标端口 50698**，脚本中不要写死 22。连接信息见本机 `password.md`（不入库）。
- 2026-08-05：中间件服务器 `/tmp` 报 `Structure needs cleaning`（文件系统错误），无法写入，
  部署脚本已改用 `/root` 作临时目录。**该文件系统需排查后 fsck**，属未解决的遗留隐患。

## 2026-07-26：Gateway 请求追踪与统一错误

### 已完成

- 新增 `X-Request-ID` 中间件。
- 客户端提供合法长度的请求 ID 时原样透传；未提供或超过 128 字符时自动生成。

- 未知路由统一返回 JSON 错误 `route_not_found`。
- 不支持的请求方法统一返回 JSON 错误 `method_not_allowed`，并设置 `Allow` 响应头。
- 抽取统一 JSON 响应方法，为后续 API 接口复用。

- 带 `X-Request-ID: deploy-check-001` 请求健康检查，响应头正确透传。
- 请求 `/missing` 返回 HTTP 404 和统一 JSON 错误。
- `journalctl` 已确认访问日志包含请求 ID、方法、路径、状态码和耗时。

- 客户端应保存响应中的 `X-Request-ID`，以便后续排查问题。

## 2026-08-01：文档标识变更后的旧地址重定向

### 背景

上一次做完 slug 手动编辑后遗留的问题：改标识会让已分享出去的阅读链接直接 404。语雀级别的文档系统不应让作者在「地址可读」和「链接不失效」之间二选一。

### 实现

- 迁移 `000010`：新增 `document_slug_aliases` 表记录历史标识，主键 `(project_id, slug)` 与文档表唯一键同构，两个外键均级联删除。
- 仓库新增 `FindByAliasSlug`；`Update` 在 slug 变更时把旧值写入别名表（`ON DUPLICATE KEY UPDATE` 幂等，应对 A→B→A→B 这类反复改名）。
- 阅读接口在当前 slug 查不到时才回查别名，命中则 **301** 并带 `Location` 与 `X-Document-Slug`。用 301 而非 302 是因为 slug 变更是永久的，希望中间层与搜索引擎更新记录。
- **防劫持**：新建或改名时若目标 slug 已是某个文档的历史别名，返回 409。否则旧链接会被导向错误的文档——这是安全性问题而不只是体验问题。
- 新 slug 若恰好是本文档自己的历史别名，先删除该别名避免自指向。
- 文档删除时其别名随外键级联清除，不会重定向到已删文档。
- 前端提示语相应改为「旧链接会自动跳转到新地址」。`fetch` 默认跟随重定向，前端无需其他改动。

### 验证

- Go 全量测试通过；新增 3 组测试覆盖单次改名 301、跟随后内容正确、从未存在的 slug 仍 404、多次改名后每个历史地址都指向最新、防劫持 409、删除后别名清除。
- **反向验证已做**：临时禁用重定向分支后，旧地址回 404 且测试失败，证明测试真的覆盖了这条逻辑。
- 迁移已应用到生产库与测试库；用独立测试库跑全量集成测试通过。
- 公网端到端回归 14 项全部通过：改名前 200、改名后旧址 301、`Location` 与 `X-Document-Slug` 正确、`curl -L` 跟随后拿到正文、二次改名后两个历史地址都指向 `third-slug`、占用历史标识 409、未知标识 404。
- 前端零警告；验证临时项目已清理，别名表随外键归零。

### 注意事项

- 别名只在 slug 变更时累积，没有上限与过期清理。正常使用量级下可忽略，但若有人反复改名会持续增长。
- 重定向只覆盖文档正文接口。评论等子路径仍按当前 slug 请求，前端拿到文档详情后使用的是新 slug，因此不受影响。

## 2026-08-01：修复无稳定块文档无法评论（422）

### 背景

用户在公网反馈：`POST /api/v1/projects/111/documents/doc1/comments` 返回 422，点击“发布评论”报错。

### 根因

评论创建强制校验 `documentHasBlock(document, block_id)`。而 `parseMarkdownDocument` 只把**段落和代码块**解析为稳定块，标题只进大纲。若文档正文只有标题、正文极短或为空，解析出的块为空数组。前端在文档加载时把 `selectedBlockID` 置为 `blocks[0]?.id ?? ''`，无块时即为空串；发布评论时带 `block_id:""`，后端 `documentHasBlock(document, "")` 为 false，返回 422 `block_not_found`——导致这类文档完全无法评论。

### 修复

- 后端：空 `block_id` 视为**文档级评论**（未锚定到具体块），跳过块校验；非空 `block_id` 仍必须存在。这样只有标题/无可解析块的文档也能被评论。
- 前端：评论卡片在 `quote` 为空时不再渲染空的引号（文档级评论没有引用原文）。

### 验证

- 新增 `TestCreateCommentAllowsEmptyBlock`：空 block_id 返回 201 且落库；`TestCreateCommentRejectsUnknownBlock` 仍保证非空且不存在的块返回 422。
- `gofmt`、`go test` 全量通过；前端 oxlint 零警告、Vite 构建通过。
- 随等级系统一起部署（见下条部署状态）。

## 2026-08-04：首页搜索合并入口 + 修好 ES 中文召回 + 面板重做

用户反馈「首页两个搜索都有问题，左边没反应，右边必须精准匹配，UI 很丑，为什么不支持语义搜索」。
逐条查证后是四个独立缺陷，不是一个。

### 1. 左边顶栏输入框「没反应」——不是坏了，是结果看不见

输入框绑到 `search` state，驱动 `getProjects({query})` 与客户端过滤。接口本身是好的，
实测 `/api/v1/projects?query=猫` 正确返回了猫咪项目。问题在于结果渲染在 `#project-grid`，
位于 hero + metrics 之下约两屏：用户在页面顶部打字，看不到任何变化、没有下拉、没有计数、不滚动。

### 2. 右边 ES 搜索必须精准匹配——根因是分析器只输出 bigram

内置 `cjk` 分析器的 `cjk_bigram` 默认 `output_unigrams: false`。生产 ES 实测：

```
_analyze「猫咪管理系统」→ 猫咪 / 咪管 / 管理 / 理系 / 系统   （没有任何单字）
?q=猫   → 0 条        ?q=猫咪 → 1 条
```

查询「猫」切成单字 token `猫`，索引里只有 bigram `猫咪`，两者永不相交。
凡是查询词切分与正文不对齐（单字、错位、跨词）就一律 0 命中。

**修法：精确与召回拆成两个字段。** 主字段仍用 `cjk`（只 bigram，权重高）；
新增 `.loose` 子字段用自定义 `cjk_loose`（`output_unigrams: true`，单字 + bigram，权重低）。
只开单字不行——那样「怎么部署」会命中任何含 怎/么/部/署 的文档。

### 3. 索引字段不全

`searchDocument` 原先只有 `project_name` / `title` / `body`，项目的
`summary` / `category` / `tags` 都没进索引，按标签或分类搜索是**静默失效**的
（接口 200、结果永远为空）。现已补全，且文档记录继承所属项目的这三项。

### 4. `⌘ K` 是假的

顶栏那个 `<kbd>⌘ K</kbd>` 纯装饰，全局没有任何 keydown 绑定它。
现已实现真的 ⌘K / Ctrl+K（在输入框/textarea/富文本里聚焦时不劫持），
并按平台显示 `⌘` 或 `Ctrl`——原先在 Windows 上写死 ⌘ 本身也是错的。

### 关于「语义搜索」的边界

ES 做的是**词法** bigram 匹配，本来就不是语义。真语义需要向量嵌入模型，
Claude API 不提供 embeddings 接口，需要额外的第三方服务与密钥。
**本轮已确认只做词法增强。** 因此「宠物」搜不到「猫咪」这类同义词仍不支持，
这是明确的已知边界，不是遗漏。ES 7.17 有 `dense_vector` 但没有原生 kNN，
将来要做需走 `script_score` + 一个嵌入服务，并全量带向量重建索引。

### 部署时实测发现并修掉的一个真问题

第一版把 `.loose` 段的 operator 设成了 `or`，上线后实测：
**查询「凤凰于飞」返回 4 条毫不相关的结果**——「于」是极常见字，
把「用于验证跨文档搜索的临时项目」之类全捞了出来。
改成 `operator: and`（要求全部 token 出现在同一字段）后噪声消失，
而单字查询只有一个 token，照样能命中。代价是「小猫」不再能命中「猫咪」，
用精确度换掉一个附带效果，值得。已加 `TestSearchQueryClauseRequiresAllLooseTokens` 守住。

## 2026-08-05：代码包分析（Understand-Anything 接入）Phase 0 可行性验证

需求：用户上传 ≤200MB 代码包 → 分析生成知识路线图 → 可直接放入文档发布；每用户每天 5 次。
Understand-Anything **不是 Web 服务，是 Claude Code 插件**（执行 `/understand` 产出
`.ua/knowledge-graph.json`），所以要做的是「驱动 Claude Code 的作业系统」。
先做可行性闸门，结论如下。

### 结论：原生插件路线（Path A）可行，无需协议转换代理，也无需自研编排

**DeepSeek 确实提供 Anthropic 兼容端点**，实测（不是查文档，本会话 WebSearch/WebFetch 均被网络策略拦掉）：

| 端点 | 结果 |
| --- | --- |
| `https://api.deepseek.com/anthropic/v1/messages` | **200**，返回标准 Anthropic 报文（`type:message` / `content[].type:text` / `stop_reason` / `usage`），`deepseek-reasoner` 还会返回 `thinking` 块 |
| `https://api.deepseek.com/v1/messages` | 404（所以 base URL **必须带 `/anthropic` 后缀**） |
| `claude -p` + `ANTHROPIC_BASE_URL=…/anthropic` | ✅ 正常回复 |

注意：响应里的 `model` 字段回显为 `deepseek-v4-flash`，与请求的模型名不一致，属对端映射。

### 端到端实测（7 文件 / 48KB 的 TypeScript 小仓库）

产出 `knowledge-graph.json` 18KB，`--language zh` 生效（摘要为中文）：

```
version, project, nodes(15), edges(25), layers(4), tour(7)
node.type   : document / file / function
node 字段   : id, type, name, filePath, summary, tags, complexity
edge.type   : imports / contains / exports / calls / documents
layer 字段  : id, name, description, nodeIds
tour 字段   : order, title, description, nodeIds
```

这个结构直接决定服务端渲染器（`analysis_roadmap.go`）怎么写：
`project` → 概览，`layers` → 架构分层，`nodes` → 模块清单，`edges` → Mermaid 依赖图，`tour` → 建议阅读顺序。

### **重要发现：耗时是真正的约束，200MB 是错的旋钮**

**7 个文件跑了 514 秒（8.6 分钟）**，而内存峰值只有 436MB。
也就是说瓶颈**不是内存**（8GB 绰绰有余），而是**时间与 token**。
插件自己在 `SKILL.md:271` 就有一道 **>100 文件闸门**，会建议用户缩小范围。

推论：200MB 只是上传体积上限，**真正要限的是参与分析的文件数**。
一个 200MB 的包可能有上千个文件，按当前速率会跑到小时级、token 成本也不可控。
因此后续设计要加：参与分析的文件数上限（优先入口文件与核心模块）、
分阶段进度回报、以及远大于 1800s 的超时；前端要如实告知"大型代码包只分析核心部分"。
按 5 次/人/天 + 并发 2 估算，单机吞吐约每小时 14 个作业，用户一多需要排队提示。

## 2026-08-05：域名在手机/宽带网络打不开的根因 —— 接入商备案拦截（非本站配置问题）

用户反馈手机流量打不开 `https://www.openresource.cn/`。服务端配置没问题，
问题在服务器**上游的网络设备**。以下是取证过程与结论。

### 排查方法：三个出口对比

单一出口测不出这个问题。用了三个视角：

| 出口 | `https://www.openresource.cn/` | 说明 |
| --- | --- | --- |
| 开发机（有代理） | 403 | 代理自己拦的，**不能用来判断线上状态** |
| 分析机 `103.236.97.248`（IDC） | **200**，证书正确，HTTP/2 | 这条路径没被过滤 |
| 中间件服务器（NAT 后宽带线路） | **000 / 404** | 与手机网络表现一致 |

### 取证：返回的不是 nginx

从宽带出口请求 `http://<IP>/`，拿到的响应头明显不是 nginx：

```
HTTP/1.1 404 NOTOK                          <- nginx 只会说 "404 Not Found"
Date: Sat, 31 Dec 2005 23:59:59 GMT         <- 硬编码的 2005 年
Content-Type: text/html;charset=GB2312      <- 中文地区拦截设备
```

正文标题是「该网站暂无法访问」，带一个工单码 `code:7l8yacEXs8esfm`，
并援引《非经营性互联网信息服务备案管理办法》。**这是接入商/运营商的备案拦截页。**

### 拦截机制（SNI 矩阵实测）

从宽带出口对 `103.236.98.166` 做矩阵测试：

| 目标 | 结果 |
| --- | --- |
| `:80`，Host 为域名 / 裸 IP / 无关域名 | 全部返回拦截页 → **80 端口整体被拦，与域名无关** |
| `:443`，任意 SNI 或无 SNI | `no peer certificate` → **443 整体不可用** |
| `:8443`，SNI = 任意值（含 `foo.example.com`） | `write:errno=104`（连接被重置） |
| `:8443`，**不带 SNI** | ✅ 握手成功，拿到正确证书 |

即：**只要 TLS ClientHello 里带 SNI 扩展就被重置**，不带就放行。
这也解释了为什么项目一直用 `IP:8443`（curl/浏览器访问 IP 时不发 SNI）。
拦截是**间歇性**的——access log 里能看到少量 301/200 漏过来的请求。

### 结论与待办

工信部备案通过 ≠ 接入商已放行。**需要在 IDC/云服务商侧完成「接入备案 / 域名绑定」**，
把备案号与 `103.236.98.166` 绑定，让上游解除对 80/443 与 SNI 的拦截。
提工单时带上拦截页的 `code:7l8yacEXs8esfm`。

**这不是服务端问题**：流量到达 nginx 时应答完全正确（access log 有 200/301），
证书、跳转、HTTP/2、TLS 1.2/1.3 都已验证通过。服务端无需改动。

过渡期唯一可用入口仍是 `https://103.236.98.166:8443/`（不带 SNI 才能过），
但会有证书域名不匹配告警——证书是签给域名的。

### 教训

判断线上可达性必须多出口交叉验证。这次我先用开发机（403）误判成 DNS 问题，
又用分析机（200）误判成"完全正常"，两次都错——因为两个出口都不代表真实用户路径。
宽带/移动出口才是。

## 2026-08-05（补充）：`59.82.113.122` 的真身是阿里郎/云壳，与备案拦截是两回事

用户在本机 ping 域名得到 `59.82.113.122`（归属地河北张家口阿里云），怀疑 DNS 有问题。
查证结果：**DNS 没问题，是本机的终端安全软件在劫持解析。**

### 取证

访问 `59.82.113.122` 时返回 403，正文写得很清楚：

> 抱歉，您要访问的域名不在安全策略默认允许的范围内。如果希望进一步访问，
> 请打开「云壳-防护记录-域名拦截」，点击对应域名右侧的按钮，免批加白或审批报备后即可访问。

它 443 端口的证书是 `CN = Alilang Root CA 2048 - G2` / `Alilang OA TLS Server Root`
—— **阿里郎（Alilang）是阿里巴巴的内网终端安全系统，云壳是配套的防护产品**。
也就是说这是装在开发机上的公司安全软件在做 DNS 劫持 + 域名拦截，
只作用于装了它的机器，与服务器、与 DNS 配置都无关。

### 三个位置的解析结果对比（决定性证据）

| 位置 | 解析结果 |
| --- | --- |
| 开发机（装了阿里郎的公司网络） | `59.82.113.122` ← 被劫持 |
| 分析机（IDC） | `103.236.98.166` ✅ |
| 中间件服务器（宽带） | `103.236.98.166` ✅ |

权威 NS 用不用 ECS 查都返回 `103.236.98.166`。**DNS 配置一直是对的。**

### 结论：有两层互不相干的拦截

| 层 | 特征 | 影响范围 | 谁来解 |
| --- | --- | --- | --- |
| **A. 阿里郎/云壳** | 403，正文提「云壳-防护记录-域名拦截」，TLS 证书 `Alilang Root CA` | 只影响装了阿里郎的开发机 | 自己在云壳里给该域名加白 |
| **B. 接入商备案拦截** | `404 NOTOK` + `Date: 2005` + GB2312，援引《备案管理办法》，工单码 `code:7l8yacEXs8esfm` | 公网路径：宽带、**手机流量** | 接入商完成接入备案/域名绑定 |

**手机打不开是 B 层**，与 A 层无关——手机流量不经过阿里郎。
开发机打不开是 A 层叠加 B 层，两个都要解。

### 又一次方法论教训

我前面把 `59.82.113.122` 一句话带过说"那是我这边的代理"——方向对（确实是终端侧拦截层），
但没有查证就下结论，既没说清是什么，也没给出解法。
用户拿归属地信息质疑后才真正去取证，一查正文就写着解法。
**看到异常 IP 应该先把它的响应正文和证书打出来看，而不是先猜。**
